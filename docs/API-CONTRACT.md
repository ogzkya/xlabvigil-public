Independent product `XLab Vigil`, module `xlabvigil`, cookie `vigil_session`, environment `VIGIL_*`. Existing auth endpoints /api/status, /setup, /login, /session, /logout retained. All arrays return [] when empty, error on database failure. ISO timestamps and date-only YYYY-MM-DD membership dates. All mutation inputs strict JSON, same-origin, authenticated. Admin/analyst can read/write risk objects; member/viewer cannot access these sensitive objects in this slice. Admin alone reads audit. No data is seeded in the real database except the schema; demo fixtures are browser-only.

Create/update body {kind,name,department,description,identifier,personId,expectedVersion?}. PATCH must include expectedVersion, full editable fields. GET/POST /api/entities; PATCH/DELETE /api/entities/{id}, DELETE {expectedVersion}. Reject deleting entity with memberships or linked accounts/devices; preserve evidence by not offering cascade. Do not change kind when references exist.

Membership: {id,entityId,groupId,reason,responsible,startsOn,endsOn,reviewOn,status,active,version,createdAt,updatedAt}. status = active | closed. responsible is a required human-readable reviewer name (not an access grant). source is manual in this slice; no fabricated evidence or automatic threat decision. active computed server-side from status and UTC dates; endsOn inclusive. GET/POST /api/memberships; PATCH /api/memberships/{id}. Body {entityId,groupId,reason,responsible,startsOn,endsOn,reviewOn,status,expectedVersion?}. reason >=10 chars; valid start <= review <= end, interval <=366 days; new active membership end cannot be past. Duplicate active-status membership for same entity/group ->409. Closed records retained; no delete endpoint. IDs cannot change on edit. Every mutation with append-only application history record in same transaction. This history is not independent tamper-proof storage.

GET /api/sources returns static catalog [{id,name,category,status,description}], status='not_configured' for AD directory, Windows WEF, VPN/firewall, NAC/SIEM, EDR, M365, custom API. No live connectivity or credential fields.

GET /api/audit retains existing shape [{id,actor,action,kind,createdAt}] admin only. Its legacy 1000-record maximum remains (+1 detects overflow); 422 collection_limit instead of silently truncated results. `GET /api/audit/page` is the admin-only paged alternative and returns `{items:[{id,actor,action,kind,createdAt}],nextCursor}`. Default limit 50, maximum 100; omit cursor for the first page. Supplied limit and cursor must each be one canonical positive decimal value; invalid values return 400 invalid_input. Optional `q` follows the event-search validation below and searches actor name, action code, and record kind as a case-insensitive literal substring before pagination. The UI may send up to 32 distinct `labelAction` values with `q` to include action codes whose visible Turkish labels match the phrase; these codes are exact matches and cannot be sent without `q`. Rows are ordered by descending audit ID; `nextCursor` is the last returned ID as a string when another row exists, otherwise `""`. Each page is a fresh read, not a frozen snapshot or total count. GET /api/memberships/{id}/history returns [{version,action,actor,createdAt,data}] admin/analyst, data membership snapshot. Membership create/update history plus audit transaction atomic. Its list maximum remains 1000 (+1 detects overflow); 422 collection_limit instead of silently truncated results.

Errors {code,message}; missing404, permission403, stale409, invalid_input400, unavailable503. New standalone schema with versioned migration ledger. No shared database or session access to Nexus. SSO/MFA, file export, source-specific ingestion, per-case authorization and real AD verification remain future work.

## 0.3 source configuration and normalized import

`GET /api/sources` remains a static catalogue and does not report configured connections. `GET /api/connections` is the persistent collection (maximum 500; explicit overflow error). Admin/analyst read; only admin creates/updates configurations and imports events. All new endpoints retain session, origin and strict JSON checks. No anonymous webhooks or machine-token ingest endpoint exist.

Connection: `{id,name,provider,transport,endpoint,productVersion,scope,secretRef,status,version,createdAt,updatedAt,lastReceivedAt,eventCount}`. `lastReceivedAt` nullable; `eventCount` counts accepted local imports only, never live source coverage. Providers: `ldap_ad`, `windows_wef`, `palo_alto`, `logsign`, `trend_vision_one`, `trend_apex_one`, `trend_deep_security`, `custom`. Transport is selected per provider: `ldaps`, `wef_https`, `syslog_tls`, `api_https`, `manual_json`. These are planned connection profiles, not enabled collectors. Status `configured|paused` is administrative state, never health/connection verification.

`POST /api/connections`; `PATCH /api/connections/{id}` with full configuration plus `expectedVersion`. Endpoint is optional during preparation; when present requires https/ldaps/tls matching transport and rejects URL credentials, query strings and fragments. `secretRef` is empty or `env:[A-Z_][A-Z0-9_]{0,127}`; no secret resolution/network access. Provider/transport cannot change after events have been accepted. LDAP profile cannot ingest security events.

`POST /api/events/import` accepts `{connectionId,events:[...]}` on a configured `manual_json` source. Batch: 1–100 events within the shared 128 KiB JSON limit. Event input: `{externalId,occurredAt,category,severity,title,summary,subject,device,sourceIp,entityId,originProduct,originEventId}`. Optional strings may be omitted. Time: RFC3339, required, UTC/microsecond canonicalized, no more than five minutes into the future. IPv4/IPv6 literal only. `severity=info|low|medium|high|critical`; `category=authentication|authorization|account_lifecycle|network|endpoint|email|data_access|other`. Title 2–240 chars, externalId 1–256; summary <=2000; subject/device <=256. Unknown fields and raw payloads are rejected. `entityId` is an optional existing entity UUID; association always candidate.

Response `{accepted,duplicates}`. All accepted events, source counts, notifications and audit commit atomically. Deduplication key `(connectionId,externalId)`: exact normalized replay is counted as duplicate; changed content with same key returns `409 event_id_conflict` and rolls back the entire batch. Different connections are not cross-deduplicated. origin fields record supplied provenance, not independently verified origin. No automatic group membership, risk score or enforcement.

`GET /api/events` returns `{items,nextCursor}`; default50/max100, newest accepted sequence first. Optional query parameters are `connectionId`, `severity`, `q`, `cursor`, and `limit`. Items add `{id,connectionId,receivedAt,identityState,provenance}` to input. `identityState=candidate|unlinked`, `provenance=manual_import`. Optional `q` must be omitted when there is no search; when supplied it is trimmed, must contain 3–120 Unicode characters, and may occur only once. Invalid UTF-8, control characters, and malformed query escaping return `400 invalid_input`. Search is a case-insensitive literal substring over title, summary, subject, device, source IP, origin product, external ID, and origin event ID; `%`, `_`, and backslash are treated as text. Search and source/severity filters run before keyset pagination. Omit cursor for the first page; supplied limit and cursor must each be one canonical positive decimal value. Changing any filter or `q` restarts pagination. Each request is a fresh read, without a total count or frozen snapshot; refresh the first page to see newly committed records.

`GET /api/entities/{id}/candidate-events` is an admin/analyst-only, read-only context view. It returns the same `{items,nextCursor}` and event item shape as `GET /api/events`, for events whose stored `entityId` is exactly `{id}` and `identityState=candidate`. The link comes only from the explicit entity ID supplied during manual import; it is neither inferred from names/IP addresses nor validated against an external source. A missing entity returns 404. Only optional `limit` and `cursor` are accepted; other query keys return `400 invalid_input`. They use the same canonical positive-decimal/default50/max100 rules. Omit cursor on the first page; records are ordered by acceptance sequence descending. Each page is a fresh read without total count or a frozen snapshot. This is candidate context for an entity, not evidence attached to a membership, an investigation case, or an automatic threat decision.

## 0.24 analyst-curated membership event references

`GET /api/memberships/{id}/event-evidence` is admin/analyst-only and returns `{items,nextCursor}` newest attachment first, including active and retracted references. Default page size is 20, maximum 100; omit `cursor` on the first page. Only optional canonical positive-decimal `limit` and `cursor` are accepted. A missing membership returns 404. The item includes `{id,membershipId,eventId,reason,status,attachedBy,attachedById,attachedAt,retractedBy,retractedById,retractedAt,retractionReason,event}`; `status=attached|retracted`, `event` is the original normalized event object, `retractedAt` is null and retraction strings are empty while attached. The reviewer name is captured at the action time. Pages are fresh reads without a total count or frozen multi-page snapshot.

`POST /api/memberships/{id}/event-evidence` accepts strict JSON `{eventId,reason}` and returns the new item with 201. `reason` is trimmed and must be 10–1000 Unicode characters. The server requires an existing event whose explicit candidate `entityId` equals the immutable membership `entityId`; the relation is never inferred from the event subject, host, IP, or time. An unlinked or differently linked event returns 409, as does an already active pair. Each successful attachment records the analyst, timestamp, rationale, and an application audit action in one transaction. A closed membership may receive a later, timestamped analyst reference; its original status and review dates remain unchanged. Attachment does not change the membership's reason, status, dates, group, or version.

`POST /api/memberships/{id}/event-evidence/{evidenceId}/retract` accepts strict JSON `{reason}` with the same length rule. It records the withdrawing actor, time, and explanation, keeps the original attachment, and returns the updated item. Another withdrawal returns 409; missing or unrelated evidence returns 404. After withdrawal the same event may be attached again as a new, separately recorded decision. Both actions are admin/analyst-only and are denied in the browser-only demo. These are analyst-selected investigation references; neither source authenticity nor a security conclusion is independently verified. This application history is not a tamper-proof evidence store.

## 0.25 unified membership activity

`GET /api/memberships/{id}/activity` is an admin/analyst-only, read-only view over membership history and event-reference actions. It returns `{items,nextCursor}`. Only `limit`, `cursor`, and `kind` are accepted, once each. `kind=all|membership|evidence` defaults to `all`; it filters before pagination. Default page size is 20, maximum 100, using canonical positive-decimal `limit`. Omit `cursor` for the first page. The opaque versioned cursor is bound to the membership and kind; malformed, empty, mismatched, or unknown query input returns `400 invalid_input`. Missing membership returns 404.

Each item has `{id,action,occurredAt,actorId,actor,actorNameSource}`. Actions are `membership.created`, `membership.updated`, `membership.reviewed` (added in 0.26), `membership_evidence.attached`, and `membership_evidence.retracted`. `occurredAt` is the stored application action time, not the source event time. Membership items add `version`, `after` (the saved membership snapshot), and `before` when the preceding version exists. The preceding snapshot is joined independently of pagination; a missing predecessor is not an empty snapshot. Compare only persisted editable fields: `reason`, `responsible`, `status`, `startsOn`, `endsOn`, and `reviewOn`. Computed `active`, metadata, and version counters are not user field changes.

Evidence items add `evidence:{id,eventId,title,severity,eventOccurredAt,originProduct,originEventId,provenance,identityState,reason}`. The reason is the original attachment rationale or the retraction rationale for that specific action. Attachment and retraction each have their own activity identity; a later retraction does not rewrite the original action as retracted. The event metadata retains its original manual-import/candidate meaning.

`actorNameSource=current_profile` on ordinary membership create/update history means the actor name comes from the current user profile; historical name snapshots were not stored for those rows. `recorded` on evidence actions and explicit review decisions means the name was captured with the action. Actor IDs remain available in either case. The endpoint does not invent historical identity details.

Order is stored action time descending, then source rank and local sequence descending for equal timestamps. Membership version and evidence sequence are distinct ordered branches. Each branch contributes at most `limit+1` candidates to the bounded union; the previous membership version is joined for returned history entries. The parent check and page query share one read-only repeatable-read transaction. Separate pages are fresh reads, with no frozen multi-page snapshot, total count, or transaction commit-order guarantee. Refresh the first page to see newly visible actions. Existing `/history` and `/event-evidence` contracts remain available.

Migration 10 adds membership/time/version and evidence/attachment-time/sequence indexes, plus a partial retraction-time index. It adds no event storage and does not alter historical rows. The new activity endpoint, migration, and UI have not been runtime-validated in this development slice.

## 0.26 explicit membership review decisions

`GET /api/memberships/{id}` returns the current `Membership` object to an admin/analyst, or 404. The review form uses this targeted read after a conflict so it can retain the decision draft without reloading the entire workspace.

`POST /api/memberships/{id}/reviews` is admin/analyst-only and accepts strict JSON `{decision,reason,expectedVersion,nextReviewOn?}`. `decision=continue|close`; `reason` is a separate review rationale, trimmed and limited to 10–1000 Unicode characters. `expectedVersion` must match the locked membership. `nextReviewOn` is a canonical `YYYY-MM-DD` date required for continue and omitted/empty for close. The endpoint returns 201 with `{membership,review}`. The review object is `{membershipId,version,decision,reason,nextReviewOn,actorId,actor,reviewedAt}`; `nextReviewOn` is an empty string for close and the actor name is captured when recording the decision.

Continue preserves status and changes only `reviewOn` plus version/update metadata. The next date must be after UTC today, on or after membership start, and on or before membership end. It does not silently extend the membership. An open membership ending today or earlier has no room for another future review and returns `409 review_period_ended`; adjust the membership dates separately or close it. A scheduled membership can be reviewed with a date in its validity interval. Close changes status to closed and preserves all three dates. Open active, scheduled, and expired memberships can be closed. Already closed memberships return `409 membership_closed`; this endpoint does not reopen them. Stale versions use the existing 409 response; invalid decisions, rationale, or dates return 400. Missing records return 404.

Both decisions preserve the existing membership reason, responsible person/team, entity/group, start date, and end date. The server locks the membership and atomically updates its version, appends one `membership_history` row with action `reviewed`, stores the review metadata, and writes audit action `membership.reviewed`. A retry using the old expected version cannot create a second decision. No notification delivery, account access change, external-source validation, or automatic threat classification occurs.

The activity endpoint exposes one `membership.reviewed` item with existing `before`/`after` snapshots and `review:{decision,reason,nextReviewOn}`. Its actor name source is `recorded`. It participates in the membership filter and existing history cursor order; no duplicate `membership.updated` activity is generated for the same review. The legacy history endpoint can now return `action=reviewed`; the separate rationale is available from activity and the review POST response.

Generic `PATCH /api/memberships/{id}` retains its existing status/date editing contract and emits `membership.updated`. Such an edit does not imply that a separate review decision was recorded. The review rationale requirement applies to the dedicated review endpoint.

Migration 11 extends the membership history action constraint and adds `membership_reviews`, keyed by membership ID/version and linked to that exact history row. Historical rows are not backfilled as decisions. This slice has not been tested, built, browser-validated, or applied to a running database.

## 0.27 review queue presentation and workspace refresh

The review queue uses the existing full `/memberships` collection; it introduces no API route or migration. Its existing maximum of 1000 with explicit 422 overflow remains in effect. Counts are derived only after a successful full workspace read, with the current search/group scope applied before queue bucket counts. The queue does not silently accept a partial first-1000 result.

Using one browser UTC date per render, the UI classifies closed memberships first, then open memberships whose end date is before today, then overdue/today review dates, then dates from tomorrow through today+7 inclusive, and finally later dates. Scheduled open memberships can appear in the upcoming bucket. This schedule classification does not depend on the computed `active` boolean and does not modify membership state. The attention queue combines expired-open, overdue, and today; it orders by review date, end date, then membership ID. Expiry is not closure or proof that a review decision occurred.

Transient workspace refresh failure retains the last snapshot only to preserve open forms. The main content shows the failure instead of current counts, and modal notices expose retry. Editor, membership decision, and event-reference writes are blocked until a full workspace refresh succeeds; their drafts remain mounted. A targeted membership GET does not certify the other workspace collections. Authentication/authorization failures clear cached workspace and dialog selections. These frontend changes have not been built or runtime-validated.

## 0.28 latest explicit review context

`GET /api/memberships/{id}/reviews/latest` is admin/analyst-only and returns `{review:null}` when the membership exists but has no explicit review decision, or `{review:{membershipId,version,decision,reason,nextReviewOn,actorId,actor,reviewedAt}}` for the highest recorded review version. A missing membership returns 404. The membership existence check and latest decision read use one repeatable-read snapshot. The endpoint reads only `membership_reviews` and does not infer decisions from ordinary membership edits or the review date. A saved decision's actor name is the name recorded at decision time. The form shows loading, error/retry, no-decision, and latest-decision states separately. This read does not alter the membership, infer external-source validity, or prove a live review process.

## 0.3 inbox and mail preparation

High/critical imported events create one shared analyst/admin inbox notification per event in the same transaction. `GET /api/notifications` returns `{items,nextCursor,unreadCount}`; default50/max100. Optional query parameters are `cursor`, `limit`, `q`, and `unread=true`. Item `{id,title,body,severity,eventId,createdAt,readAt}`; readAt nullable and personal to the signed-in user. Optional `q` follows event-search validation and searches title/body as a case-insensitive literal substring. Omit `unread` for all items; if present, it must occur once with value `true` and returns only items not read by the signed-in user. Both filters run before cursor and limit. Omit cursor for the first page; supplied limit and cursor must each be one canonical positive decimal value. `unreadCount` always counts all unread items for that user, independent of `q`, `unread`, and the current page. Per-response items/count use one database snapshot; pagination across requests is not a shared snapshot. `POST /api/notifications/{id}/read {}` retains the first read time and audits transactionally. Member/viewer have no access.

`GET /api/notification-settings` admin/analyst; `PUT` admin only. Returned `{provider,host,port,fromAddress,recipient,secretRef,version,status}`; provider `none|smtp|graph`, status always `delivery_disabled`. PUT replaces fields and requires `expectedVersion`; stale409. Initial provider none/version1, blank strings/port0. None requires empty fields; SMTP requires hostname/IP, port465 or587 and one plain sender/recipient email address; Graph requires empty host/port0 and mailbox sender/recipient. Configured providers require `env:[A-Z][A-Z0-9_]{2,95}` secret reference. No passwords/tokens accepted, resolved or returned. Port25 relay, Graph tenant/application configuration, workers, retries, delivery status and team chat remain future work. Saving channel configuration never sends a message.

Migrations 2–11 append source/event/inbox/configuration and user-lifecycle fields, followed by `pg_trgm` GIN indexes for event, notification, and audit search, audit actor indexes, a partial entity/sequence index for candidate events, the membership event-reference ledger, activity timeline indexes, and explicit review decisions; original migration1 is unchanged. Migration 5 requires `pg_trgm` availability; a new installation requires permission to install it in `public`, while existing installations resolve the extension schema from the PostgreSQL catalogue. The migration ledger checks each numbered schema checksum. The singleton disabled notification settings row is the only seeded configuration; entity, event, source, notification, and user records are not seeded by migration.

## 0.4 local user lifecycle

`GET /api/users` lists at most 500 local users and is admin-only. The response is `{id,username,name,role,active,version,createdAt,updatedAt}`; overflow returns the standard explicit collection limit error. Usernames remain immutable after creation. No session token, password, password hash, or secret is returned.

`POST /api/users` is admin-only and accepts `{username,name,password,role}`. Username is normalized to lowercase and must match `[a-z0-9][a-z0-9._-]{2,63}`; name is 2–100 characters; initial password is 12–128 bytes; role is `admin|analyst|member|viewer`. Passwords use the existing Argon2id hash format. Duplicate usernames return `409 duplicate_username`.

`PATCH /api/users/{id}` is admin-only and accepts the full update `{name,role,active,expectedVersion}`. Username is not editable; updates use optimistic version checks. There is no hard-delete or password-reset endpoint in this slice. Administrators cannot change their own role or deactivate their own account. The last active admin cannot be disabled or moved to another role. Role or active-state changes revoke all sessions for that user in the same transaction. Creation and updates append an application audit record atomically. This audit table is not independent tamper-proof storage.

`POST /api/users/{id}/sessions/revoke` accepts `{}` and is admin-only. It revokes that other user's unexpired sessions without changing the account or role, returns `{revoked}`, and writes an audit record in the same transaction. Administrators cannot revoke their own session set through this endpoint; they can log out or use the password-change flow to close other sessions.

Migration 4 adds `active`, `version`, and `updated_at` to existing local users; existing accounts remain active. Authentication rejects inactive accounts even if a stale session row exists. SSO, MFA, production HTTPS, administrator password resets, and finer-grained authorization remain future work.

`POST /api/session/password` is available to any active signed-in user and accepts `{currentPassword,newPassword}`. Both values are limited to 128 bytes; the new password must contain at least 12 bytes and differ from the current password. The current password is verified before updating. A per-remote-host limiter allows 20 change attempts per 15 minutes. The current session remains valid; all other sessions for that user are revoked in the same transaction. User version and `updated_at` advance, and `session.password_changed` is audited atomically. Concurrent password changes are rejected with `409 stale_password` after rechecking the stored hash under a row lock.
